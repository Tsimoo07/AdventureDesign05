# 밥길 혼잡도 백엔드 설계안

**결정 제안:** 제1학생회관 한 곳에서 시작한다. ESP32-C3가 보내는 구간별 BLE 관측 통계를 서버가 현장 기준 자료와 비교하고, PWA에는 **구역별 추정 단계, 식당 전체 요약, 관측 시각**만 제공한다. 측정이 끊기거나 판정할 근거가 없으면 ‘원활’ 대신 ‘판단 보류’로 응답한다.

근거는 팀의 「창의작품경진대회 결과보고서」 2~4쪽과 포스터의 ‘시스템 구성·핵심 기술’이다. 두 자료의 수신점 배치와 k-NN은 **제안된 방식**이며 검증된 정확도가 아니다. 아래 API, 집계 규칙과 운영 목표는 밥길에 연결하기 위한 신규 설계다.

## 누가 무엇을 판단하는가

- 학생은 출발 전에 식당 전체 상태와 측정 시각을 보고 방문 여부를 정한다. 전체가 보통이어도 주문대만 혼잡한 경우를 볼 수 있어야 한다.
- 장치 담당자는 수신기 고장과 ‘장치는 정상이나 분류 불가’를 구분해 점검한다.
- 분석 담당자는 날짜를 분리한 현장 기록과 추정 결과를 비교해 공개 여부를 정한다. BLE 광고 수는 사람 수가 아니므로 인원수·좌석 점유율·예상 대기시간을 제공하지 않는다. 개인 단말 추적, 로그인, 버스 연동도 범위 밖이다.

## 수집 → 분류 → 공개

1. **장치:** 같은 UTC 경계의 관측 창마다 광고 수, RSSI 중앙값, 강한 신호 수, 실제 스캔 시간을 집계해 Wi-Fi로 전송한다. 원시 광고, MAC 주소, 단말 이름은 전송·저장하지 않는다. 반복 수신은 관측 빈도의 일부이고, 같은 통계 묶음의 재전송만 중복 제거한다.
2. **수집 API:** HTTPS와 수신기별 폐기 가능한 자격증명을 사용한다. 장치의 구역은 서버의 설치 목록에서 찾는다. 시간·수치·장치 권한 검증 후 영속 DB에 기록해야 성공을 반환한다.
3. **분류:** 같은 창의 기준 수신점과 지정된 인접 수신점을 결합한다. 특징은 초당 관측 수, RSSI 중앙값, 강한 신호 비율, 그 비율과 인접점 평균의 차이다. 학습 자료로 구한 평균·표준편차로 표준화한 뒤 동일 구역의 기준 벡터와 유클리드 거리를 계산하고 가까운 k개 라벨로 투표한다. 분산이 0인 특징은 제외한다. 표본 부족, 필수 인접점 누락, 동률, 기준 자료에서 너무 먼 입력은 판단 보류다.
4. **저장·배포:** 제안 구성은 기존 Vercel 프로젝트의 수집·조회 함수와 외부 PostgreSQL 한 개다. 첫 식당에서는 창 입력이 도착할 때 해당 창의 영향 구역만 재계산한다. 최신 결과는 관측 종료 시각이 더 오래된 결과로 덮지 않는다. 만료 여부는 조회 시 계산해 장치가 완전히 멈춰도 과거 결과가 현재값이 되지 않게 한다.

## API와 저장 계약

| 경로 | 계약 |
|---|---|
| POST /api/observations | 장치 전용. 예: `{"windowStart":"2026-11-18T03:00:00Z","durationSec":30,"scanSec":29,"count":90,"strongCount":24,"medianRssi":-72,"configVersion":1}`. 창 길이·경계와 임계값 버전은 등록 설정과 일치해야 한다. 0 ≤ strongCount ≤ count, 0 < scanSec ≤ durationSec. count=0이면 중앙값은 null이며 빈 식당으로 판정하지 않는다. |
| 수집 응답 | 최초 저장 201, 동일 재전송 200, 같은 수신기·창에 다른 값 409. 잘못된 본문·미래 시각 400, 미인증 401, 비활성 장치 403, 과다 요청 429. 장치는 일시적 장애만 지연 재시도한다. |
| GET /api/categories, GET /api/categories/:id | 공개 읽기. 목록과 단건은 같은 식당 스키마를 사용한다. 미등록 식당 404, 정상 식당에 자료가 없으면 200과 unknown, DB 장애는 503. 응답 캐시는 시범 단계에서 no-store. 장치 ID와 특징 벡터는 공개하지 않는다. |

**공개 응답 예시** (단계형 계약으로 전환한 뒤):

```json
{"id":"1","label":"제1학생회관","updatedAt":"2026-11-18T03:00:30Z",
 "overall":{"level":"unknown","reason":"partial","measuredZones":1,"expectedZones":2},
 "items":[{"id":"2","label":"식사구역 1","level":"warning","observedAt":"2026-11-18T03:00:30Z"},
          {"id":"3","label":"식사구역 2","level":"unknown","reason":"offline","observedAt":null}]}
```

구역 ID는 기존 평면도·즐겨찾기와 동일하게 유지한다. 단계는 normal(원활), warning(보통), danger(혼잡), unknown(판단 보류)이다. **전체 단계 제안:** 같은 창에서 운영 중인 측정 대상 구역이 모두 유효할 때만 구역 단계의 중앙값을 제공한다(짝수면 더 혼잡한 쪽). 부분 수신이면 구역 결과는 보여주되 전체는 보류한다. 영업 준비 중은 센서가 추정할 수 없으므로 별도 운영 정보로만 처리한다. updatedAt은 마지막 관측 창의 종료 시각이며, 수신 시각이나 조회 시각이 아니다. 최초 미측정은 null이다.

**기존 화면과의 차이:** 현재 [타입](../my-pwa-app/src/features/status/types.ts)은 숫자 value를 요구하고 [상세 화면](../my-pwa-app/src/pages/CategoryPage.tsx)은 이를 평균 내 %로 표시한다. 세 등급을 가짜 백분율로 변환하지 않는다. 운영 전 목록·상세·즐겨찾기의 타입, 검증기, 단계 표시를 함께 전환하고 전체는 overall을 읽게 한다. 기존 조회 경로에 맞춰 VITE_API_URL=/api 를 사용한다. 화면의 작은 회색 시각은 관측 시각을 KST로 변환하며, 만료 시 ‘마지막 측정’으로 구분한다.

| 저장 단위 | 키와 보존 원칙 |
|---|---|
| 설치 설정 | 식당·구역·수신기 매핑, 인접 수신점, 유효 기간, 설정 버전. 장치 교체·이동 시 버전을 올린다. |
| 관측 창 | (수신기 ID, 창 시작) 유일 키. 집계 통계·수신 시각만 보관. 시범 보존기간 제안 7일, 만료 삭제. |
| 기준 자료·모델 | 구역, 현장 관찰 단계, 창, 특징값, 설치·모델 버전. 표준화 계수·k·보류 기준을 함께 버전 관리한다. |
| 분류 결과 | (구역, 창, 모델 버전), 단계·보류 이유. 최신 창을 인덱싱하고 공개 조회 계정은 읽기만 허용한다. |

## 우선순위·검수

| 순위 | 완료 기준 |
|---|---|
| P0 수집·보호 | 등록 장치의 같은 창을 두 번 보내도 행은 하나다. 폐기한 키로는 쓸 수 없고 공개 응답·로그에는 키와 BLE 식별자가 없다. |
| P0 분류·표시 | 기준 자료 없는 구역, 표본 0, 수신기 단절을 각각 재현한다. 어느 경우도 원활로 응답하지 않는다. 정상 수신 복구 후 다음 유효 창에서 결과가 복구된다. |
| P0 전체·시각 | 두 구역 중 하나만 수신하면 전체는 보류, 유효 구역은 표시된다. 역순 패킷이 도착해도 표시 시각이 과거로 돌아가지 않는다. |
| P1 운영 점검 | 담당자가 수신기별 마지막 수신 시각, 누락 창 수, 보류 이유를 조회해 점검 대상을 찾는다. |
| P2 타 식당 확대 | 제2학생회관의 설치 매핑과 별도 현장 기준 자료로 검증을 통과한 뒤 공개한다. 제1학생회관 기준을 그대로 복제하지 않는다. |

## 검증 목표와 순서

1. **설치 전 — 장치·시설 담당, 착수 조건:** 설치·Wi-Fi 사용 승인을 받고 주문·배식·식사 구역, 인접점, 운영 시간을 확정한다. 첫 시험값은 30초 창, 2개 창 경과 시 만료로 제안한다. RSSI 기준과 실제 스캔 가능 시간은 현장에서 정한다.
2. **비공개 시범 — 분석 담당:** 관찰자가 같은 시각의 대기열·좌석 상태를 세 단계로 기록한다. 학습일과 검증일을 분리하고 k, 거리 한계, 최소 관측 수는 검증일 평가 전에 고정한다. 인접점 차이를 뺀 모델과 포함한 모델을 같은 자료로 비교한다.
3. **공개 판단 — 팀 합의 필요:** 잠정 목표는 정상 창 수집 후 공개 API 반영 p95 15초 이내, 만료 상태를 정상으로 표시한 시험 0건이다. 시범 1주 후 날짜별 혼동행렬로 실제 혼잡을 원활로 안내한 비율 5% 이하, 운영 창 중 보류율 20% 이하를 각각 확인한다. 표본 수와 구역별 결과를 병기하고, 실제 혼잡 사례가 부족하면 통과로 처리하지 않는다. 이는 달성 결과가 아닌 출시 판단 제안이다.
4. **운영 전 — 제품·데이터 담당:** 전체 단계에 일부 구역의 혼잡이 가려지는지 확인하고 요약 규칙을 승인한다. 설치 위치·모델이 바뀌면 재검증한다. 확정 출시일은 없으며 데이터 확보·검증이 선행 조건이다.
